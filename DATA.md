# Data

The release asset `jointdw_data_v1.2.tar.gz` unpacks to `data/`. It holds every file of `jointdw_data_v1.1.1.tar.gz` (release v1.1.1), with three changes: this file, `reference_results/` (the results of the present scoring, below), and the user message of the 405 recorded prompts that embed a complete benchmark instance (below, Benchmark data), which is left out. It adds the records of the time-optimal decompositions on the benchmark instances, the rich models with 12 and 16 families, the classes without a joint group (generalized assignment and bin packing), the time of one evaluation per collection and the cost accounting. The sample of record of the earlier experiments is dated 2026-11-07; the added records are dated 2026-11-08 and 2026-11-09, and every table is scored under the rules below. `scripts/fetch_data.sh` downloads the archive and checks its SHA-256 against the value recorded in the script; `scripts/reproduce.sh` builds every table and figure from it without a solver or a language-model call, and `scripts/compare_results.sh` compares the result with `data/reference_results/`.

## Records

Request and response records are kept as they were sent and received, with one change: each usage object keeps only the standard token fields (prompt, completion and total tokens, cached prompt tokens and reasoning tokens), and the other fields that the endpoints added, among them billing fields, are removed. The records contain no keys and no endpoint addresses. The responses of GPT-6.1 Sol on the rich models, in the data variant and in the ranked variant carry the snapshot identifier returned by the API, `gpt-6.1-sol-2026-09-29`; its responses on the templates and MIPLIB-NL name `gpt-6.1-sol`.

The added call records follow the same rule, with the cache-write counts of the cost accounting kept as two fields of the usage object (`cache_write_5m_tokens`, `cache_write_1h_tokens`, written only where they are not 0); every billing object is removed. A retried attempt (time out, a network or gateway error, an incomplete answer) is one line of `llm_retries.jsonl`, as in the earlier release.

Every request has a cache entry. For 463 answers the request is byte-identical to the request of another instance, the cache holds one response for both, and each answer file holds the parsed answer of its own instance.

## Bound validity

The recorded evaluations are kept as they were returned. Every table reads them through one rule (`llmdw.scoring.bounds`): a recorded dual bound counts as no bound when it is not finite or at least 1e19 in absolute value, when it is beyond the reference optimum, or when it is beyond the best primal solution value recorded by SCIP in any evaluation of the same model, each by more than the tolerance max(1e-4 x |optimum - LP bound|, 1e-4 x max(1, |optimum|)) (without a reference optimum, 1e-4 x max(1, |primal value|)). The invalid bounds are flagged in `reference_results/census_evaluations.csv` and `reference_results/large_models_invalid_bounds.csv`. A reference optimum that a recorded primal solution contradicts by more than the same tolerance was replaced by the optimum that SCIP proves (one thread, seed 0, 3600 s; `census_corrections.json`, `work/reference_optima/`): b-ball, a maximization, from 1.5 to 3.0, and radiationm18-12-05, a minimization, from 17574 to 17566. No recorded bound lies beyond either new reference.

Under the rule the greedy forward selection of two large models takes another path. On sct31 it stops after the nine single families; on sct32 it needs one set that had not been evaluated, which was evaluated once in the census setting (GCG root node, SCIP propagation off, 120 s, one thread, seed 0, 10 GB): `work/large_models/sct32/evals/`, the convexified families cap[#] and pbudget, status time limit, bound -62.99083349240084. This is the only evaluation added to the records of the earlier release.

## Validity of branch-and-price runs

Every branch-and-price run of the standard formulations, the time-optimal decompositions and the classes without a joint group (every set and seed, GCG with its own detector, SCIP alone) is read through one rule (`llmdw.benchmark.validity`), with the reference optimum z* below and the tolerance of the bound validity rule. A run that reports optimality counts as solved only if its reported optimal value is within the tolerance of z*. A run that reports optimality at a value worse than z*, or ends with a dual bound beyond z*, each by more than the tolerance, has an invalid dual bound and counts as failed under the failure rule of the time-optimal decompositions: unsolved at the 1800-second limit (1801 s in the time statistic), its root bound kept only if the bound validity rule accepts it, and its final gap computed from that root bound, or from the LP bound when the root bound is rejected. A run with a solution better than z* by more than the tolerance is checked for feasibility: its solution (written by a rerun of the same set and seed with solution output when the run wrote none, `bnp/solution_check/`) is checked against every row of the model as built, the variable bounds and integrality, with absolute tolerance 1e-6; a feasible solution becomes z* and the two conditions above are applied again to every run of the instance, an infeasible one makes the run failed. The recorded runs are kept as they were returned; the status after the rule is a column of `reference_results/experiment_D/bnp_runs.csv` and `experiment_F/bnp_runs.csv` (`status`, with `status_recorded`, `validity_rule`, `reported_value` and `z_star`).

Runs with an invalid dual bound, counted as failed: fl_cap43 with {Link}, seeds 0 to 2 (reported 1,158,169.046 against the proved optimum 1,153,000.45); fl_cap112 with {Link}, seed 2 (904,198.616 against 901,377.2125); bp_u120_02 with {Assign, Capacity}, seeds 0 to 2 (47 bins against 46, proved by SCIP); bp_u120_06 with {Assign, Capacity}, seeds 0 to 2 (49 bins against the best-known count 48). Runs with a better solution: bp_u120_19 with {Capacity} and with GCG's own detector, seeds 0 to 2 (49 bins against the earlier reference 50); the 49-bin packing of each rerun is feasible (every one of the 219 rows, every item in exactly one bin, every bin load at most the capacity 150), and z* of bp_u120_19 is 49. No run of the standard formulations meets either condition.

## Reference optima

The reference optimum z* of an instance of the benchmark collections is the best of the value proved or found by SCIP (`reference.json`: SCIP defaults, one thread, seed 0, 3600 s), for bin packing the best-known count of the OR-Library file (`meta.json`, `size.best_known_bins_in_file`), and a branch-and-price solution accepted by the feasibility check above (`reference_accepted.json`). The same z* is used for the gains, the gain shares, the bound validity rule and the validity of branch-and-price runs. On the benchmark instances of the standard formulations it is the SCIP value on every instance. On generalized assignment it is the SCIP value (every one equal to the published optimum in the model's sense, `gap_published_check.json`). On bin packing it is below the SCIP value on 11 of the 16 instances: on 10 the best-known count of the file (bp_u120_00, 03, 05, 06, 07, 09, 11, 15, 17 and 18, each one bin below SCIP's best solution, which SCIP did not prove), and on bp_u120_19 the feasible 49-bin packing of the branch-and-price run of {Capacity}, seed 0, where SCIP found 50 without proof and the file states 50; ceil(sum of sizes / capacity) is 49 on that instance. These values are listed with their sources in `reference_results/experiment_F/instances.csv`.

## Benchmark data

The benchmark instances are built from public benchmark files, which this archive does not contain: the pages of the sources state no license that permits redistribution, so the files are fetched from their original locations, and the model files built from them are not in the archive either (the gain tables, ground truth, branch-and-price records and answers are). `scripts/fetch_benchmarks.sh` downloads them from their original locations into `data/benchmark_raw/` and checks every file against the SHA-256 recorded when the instances were built (`config/benchmark_sources.json`); `python -m llmdw.benchmark.standard build` then rebuilds the 219 model files of the standard formulations, whose SHA-256 is recorded in each `meta.json`, and `python -m llmdw.benchmark.standard check` verifies them against it.

The classes without a joint group are built from OR-Library files in the same way: `scripts/fetch_benchmarks.sh` also downloads gap1 to gap12 with `gapinfo.html` and binpack1 with `binpackinfo.html` into `data/benchmark_raw/orlib_gap/` and `data/benchmark_raw/orlib_binpack/`; `python -m llmdw.benchmark.extra_classes build` rebuilds the 80 model files (60 generalized assignment, 20 bin packing; their `model.mps`, `model.md` and `instance.json` are not in the archive) and `python -m llmdw.benchmark.extra_classes check` compares the SHA-256 of each with the one recorded in its `meta.json`. The gain tables, the ground truth, the branch-and-price records, the answers and the results are in the archive.

The data variant on the benchmark instances sends the complete instance in CPLEX LP format inside the user message. That message is left out of the 405 answer files that hold it (`work/benchmark_std/answers_data/`, 354, and `work/benchmark_std/rejected_added_text/answers/`, 51): its content is null and the field `user_message_left_out` says how to recreate it; the system message, the answer and every other field are kept. `llmdw.prompts.propose.build_messages` with the `with_data` template recreates the message from the rebuilt model file; for every one of the 405 files the recreated messages are identical to the recorded ones. Release v1.1 and v1.1.1 published these messages; their archives are unchanged.

### Run setting of the benchmark data variant

The client rejects an answer whose reported prompt tokens exceed a factor per prompt character plus 300 tokens (`llmdw.providers.llm_client.inflated_prompt_tokens`; the factor of each configuration is `prompt_tokens_per_char` in `config/public_settings.json`, 0.45 for GPT-6.1 Sol and 0.65 for Claude Sonnet 5.5): an endpoint that adds text to the request reports more prompt tokens than the request holds. For the data variant on the benchmark instances the factor was 0.50 for GPT-6.1 Sol and 0.85 for Claude Sonnet 5.5, for this run only (`--prompt-tokens-per-char`), because of the digit density of the LP text: 17 to 24 percent of its characters are digits (at most 7 percent in the data variant on the rich models), and numbers take more tokens per character, so the true prompt tokens exceed the configured factors (GPT-6.1 Sol 0.411 to 0.467 tokens per character, Claude Sonnet 5.5 about 0.68 to 0.78). Nothing that is sent changed, and the 300-token slack, the check that repeated samples of one request report the same prompt tokens within 5 tokens, the retry rule of GPT-6.1 Sol and the stop rule of Claude Sonnet 5.5 are those of every other run. Under the configured factors the run had stopped after two answers of Claude Sonnet 5.5 (ls_F1 and ls_F2, first sample) were rejected; these two requests were sent again. From 2026-11-07 15:00:25 on, the client timeout of Claude Sonnet 5.5 in this run was 600 s instead of 1800 s (`--timeout`): of the 427 recorded answers of Claude Sonnet 5.5 before the change (the data variant on the rich models, the control presentations, the standard formulations on the benchmark instances and this run), every attempt that returned took at most 291 s, and 72 answers had one or more attempts that returned nothing within 1800 s (11 of them more than one) and then succeeded in 108 to 271 s. The timeout only bounds how long the client waits; nothing that is sent changes.

**Exact-count check of GPT-6.1 Sol.** The prompt tokens that GPT-6.1 Sol reports for a request equal the tiktoken `o200k_base` count of its messages plus a constant of the run: 10 for the runs of 2026-10-30 to 2026-11-02 (templates, MIPLIB-NL, rich models under the original prompt and the data variant, ranked variant) and 42 from 2026-11-03 on (the standard formulations on the benchmark instances, the control presentations, the data variant on the benchmark instances). Every one of the 2,028 recorded GPT-6.1 Sol records of the sample of record matches its run's constant exactly.

**Added text on the benchmark data variant.** Of the first 175 accepted answers of GPT-6.1 Sol in this run, 51 report exactly 4,212 prompt tokens more than the exact count: the endpoint through which GPT-6.1 Sol is requested added text to these requests, all of them network-design or facility-location prompts (48.5 percent of the responses on those prompts; none on lot sizing), and the raised factor did not catch it on prompts of this size. When the first sample of a request carried the addition, the repeat-sample check rejected the clean later samples, which left two requests without an answer. The 51 answers and their cache entries are kept in `work/benchmark_std/rejected_added_text/` (with `gpt-6.1-sol_set_aside.json`, the list and the replaced prompt-token references) and are not scored. Every GPT-6.1 Sol request of this run was then given its exact count as the reference of the repeat-sample check (`llm_cache/prompt_tokens/request/`, tolerance 5), so that any response with added text is rejected and retried under the retry rule of GPT-6.1 Sol, and the 51 requests and the two without an answer were sent again. In the resend none of the 53 responses carried the addition and none was rejected. In all, GPT-6.1 Sol answered 247 requests in this run: 177 accepted answers, 51 set aside for added text and 19 rejected by the repeat-sample check (14 that carried the addition, against a clean first sample, and 5 clean samples, against a first sample that carried it); every accepted answer reports exactly the exact count plus 42.

**Ratio check of Claude Sonnet 5.5.** Claude Sonnet 5.5 has no local tokenizer; its reported prompt tokens are checked against the GPT-6.1 Sol exact count of the same messages: an answer fails when it exceeds the lowest Claude/GPT ratio of its experiment and class times the GPT exact count by more than 1,000 tokens (an addition of the observed kind would exceed it by thousands of tokens). In the sample of record, 9 of the 2,028 Claude Sonnet 5.5 records with a GPT counterpart exceed this limit: the original presentation of swath1, swath2 and swath3 (three samples each), by 46 to 70 tokens. For MIPLIB-NL the margin was derived from the lowest ratio of the whole MIPLIB-NL set (bnatt500, 1.404), while these prompts have a ratio of 1.729 to 1.730, in line with similar prompts of the same presentation (1.722 for neos-2657525-crna, neos-2624317-amur and neos-2652786-brda; 1.48 to 1.49 for the other presentations of swath), and their counts are identical across samples; they stay in the sample of record. The 177 answers of Claude Sonnet 5.5 in the data variant on the benchmark instances pass the same check (lowest ratios 1.654 for lot sizing, 1.649 for network design and 1.621 for facility location; no answer exceeds the limit), so none was set aside or sent again. In all, Claude Sonnet 5.5 answered 182 requests in this run: 177 accepted answers, 2 rejected by the prompt-token guard under the configured factor (sent again) and 3 rejected because they reported no reasoning (`LLMDW_REQUIRE_REASONING`, retried); 25 attempts returned nothing within the client timeout (10 at 1800 s, 15 at 600 s) and were retried. After the change of the timeout, every attempt that returned took at most 309 s.

## Classes without a joint group

The instances are every instance of gap1 to gap12 (60, families Assign and Capacity; the files are maximization problems, written with negated objective coefficients and minimized) and the instances of binpack1 that pass the selection rule of the standard formulations (LP relaxation feasible, positive LP gap against the SCIP reference of one hour): 16 of the 20; bp_u120_01, 08, 10 and 12 have no SCIP reference value within 3600 s. Bin packing uses the Kantorovich formulation with as many bins as the first-fit-decreasing packing uses, with the families Assign (each item in exactly one bin), Capacity (the sizes in a bin at most the capacity if the bin is used) and SymmetryBreaking (y_j >= y_j+1).

Budget rule. Each evaluation convexifies at most k - 1 families. On bin packing the set {Assign, Capacity} (only the symmetry-breaking rows in the master) and on generalized assignment the pair of both families (the whole program) lie outside the budget: their bound is the integer optimum, they are recorded as outside the budget, never as the best set, and the time-optimal set is chosen among the planned sets within the budget. A method whose first set is outside the budget has gain 0 in every pooled gain, is counted in its own column (`set_outside_budget`), keeps its own measured time in the time ratios and is a miss for hit@1 against the time-optimal set.

No instance of these classes has a joint support within the budget. Capacity alone closes the whole gap on 18 generalized-assignment instances; on the other instances, the rest of the gap is closed only by {Assign, Capacity}, which lies outside the budget.

Four bin-packing instances, bp_u120_02, 06, 09 and 13, are not scored against the bound-optimal set: on each, every valid set within the budget has gain 0, so the bound-optimal set is a tie among all of them, broken by name. They are kept in every other measure.

## Lot sizing prompts and the latency of a request

Under the original presentation the 20 lot-sizing benchmark instances have byte-identical prompts: one prompt group, one request per configuration and sample, and 19 answers per configuration and sample read from the cache. In the cost accounting one prediction is the request that produced the answer of a cell, and an answer read from the cache takes the latency and the cost of the request that was sent; the latency of that one request is therefore charged to each of the 20 instances. The bootstrap draws the 20 instances as one prompt group and then resamples them within it.

## Prices

The cost accounting prices every request at the list price on the day of the request (the start time, log time minus latency, in local time), in US dollars per million tokens, from the provider's pricing page: the page as captured on 2026-11-08 and 2026-11-09, and for earlier days the Internet Archive snapshot of the same page (the last snapshot on the day, else the nearest before, else the nearest after). Cached-input prices apply only where the usage records cached prompt tokens, cache writes are priced at the 5-minute write price, and DeepSeek-V4-Pro (Non-Thinking) is priced at its peak or off-peak rate by the UTC start time. ## MIPLIB-NL
